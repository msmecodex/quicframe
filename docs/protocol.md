# Protocol

QuicFrame uses a binary wire protocol over QUIC streams. Payloads are MsgPack encoded and framed with a fixed-size length prefix.

## Frame Layout

Each frame is written as:

```text
[4B big-endian length][1B frame type][msgpack payload]
```

The length includes:

- the 1-byte frame type
- the encoded payload bytes

Maximum frame size is `64 MiB`.

## Frame Types

| Type | Value | Purpose |
| --- | --- | --- |
| Request | `0x01` | Client starts a call |
| Response | `0x02` | Server sends a non-streaming reply or stream header |
| StreamData | `0x03` | Server sends a stream chunk |
| StreamEnd | `0x04` | Server ends a stream |
| Error | `0x05` | Either side reports an error |
| Ping | `0x06` | Liveness probe |
| Pong | `0x07` | Ping response |

## Request Payload

```text
id      string
method  string
path    string
headers map[string]string
body    bytes
stream  bool
```

Notes:

- `id` is generated by the client.
- `body` is typically MsgPack again, containing your application data.
- `stream=true` tells the server the client expects a streamed response.

## Response Payload

```text
id      string
status  int
headers map[string]string
body    bytes
stream  bool
```

Notes:

- `id` matches the request ID.
- `status` uses HTTP-style semantics like `200`, `404`, and `500`.
- `stream=true` means `StreamData` frames will follow.

## Stream Payload

```text
id    string
seq   uint64
data  bytes
final bool
```

Behavior:

- `seq` starts at `0` and increases by one for each chunk.
- `StreamData` carries normal chunks.
- `StreamEnd` carries the final chunk with `final=true`.

## Error Payload

```text
id      string
code    int
message string
data    bytes
```

Application and protocol errors both use the same shape. For request-scoped failures, `id` echoes the request ID.
 
 **Note:** The Go client automatically decodes `0x05` error frames and returns a formatted error: `quicframe: server error <code>: <message>`.

## Ping and Pong

Ping and pong frames carry:

```text
ts int64
```

The Go server currently uses ping frames as a lightweight keepalive and responds with a pong frame immediately.

## Server-Side Helpers

Useful APIs in `protocol`:

- `WriteFrame`
- `ReadFrame`
- `DecodeRequest`
- `DecodeResponse`
- `DecodeStreamChunk`
- `DecodeError`
- `WriteError`

## Example Request Flow

1. Client opens a bidirectional QUIC stream.
2. Client sends a `Request` frame.
3. Server decodes and routes it.
4. Server replies with either:
   - `Response`
   - `Error`
   - `Response` with `stream=true`, followed by `StreamData` and `StreamEnd`

## Compatibility Guidance

- Keep `headers` string-only for cross-SDK compatibility.
- Treat `body` as application-defined MsgPack bytes.
- Do not assume JSON anywhere in the protocol.
